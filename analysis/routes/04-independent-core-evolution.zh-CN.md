# 独立新建多 Coding Agent 伙伴核心

## 结论

这条路线提供最大的产品与架构自主权，也承担最多从零完成可靠性的责任。应该新建的是伙伴、任务、执行、交接和成果的产品核心，复用的是原生 coding agent、协议库和经过验证的基础组件；不应把“独立”理解为重新实现模型执行循环、ACP、Git 或数据库。

建议以两个完整原生 agent、本地执行和一个真实混合协作场景起步。先证明任务能够正确继续、停止、等待用户和恢复，再加入复杂群聊、多个电脑 provider、移动端或动态插件生态。

2026-09-21 起，本路线的对象模型以 [第一性原理设计](../first-principles-cloud-agent-design.zh-CN.md) 为准：Project / Goal / Task / Run，Beads 语义做图，LoopX 合同做 tick，失败只落在 Run。下文「最小领域模型」若与该规格冲突，以规格为准。

最重要的停止条件是：如果第一阶段已经花大量时间构建通用框架，却仍无法展示一名伙伴带两个不同引擎 Worker 完成可验证工作，应缩小范围或复用已有控制面，而不是继续扩大抽象。

## 目标、假设与证据边界

目标是长期伙伴不绑定某个原生 agent，主管与 Worker 都能选择不同引擎，跨多轮工作保持历史和成果，并允许人类介入。假设首版本地优先、单用户、一个 Git 项目、两个原生引擎；服务端多用户和手机作为后续选择。

此路线没有现成基线实现。设计判断参考 Grok `a9f633e09d49`、Cindy `f4422f816ccb`、Rakazo `b286fc4a5d0f`、AO `ab968d5e7614`、Kandev `753e5549ee73`、DSH `c291e7961a51` 的源码快照。以下架构与阶段全部是建议，不是已开发功能；未作工期、成功率或成本实测。

## 从其他项目提取什么

| 来源 | 应提取的设计 | 不宜一并继承的约束 |
|---|---|---|
| Grok 重建版 | 伙伴、消息、背景工作和人类注意事项 | 原始 renderer 与恢复打包依赖 |
| Cindy | 真实能力矩阵、完整 Worker、停泊/增量交接 | Desktop 特定装配和所有历史兼容 |
| AO | native session 分离、执行权、恢复未知态 | 默认围绕 PR 的全部产品结构 |
| Rakazo | Bot/Computer/Routine、多端意图与后端状态 | 首版必须部署完整服务栈 |
| Kandev | agent 与 executor 分离、agentctl、ACP 方言层 | 一开始支持所有远端执行环境 |
| DSH | 持久事件、能力边界、插件生命周期 | 产品必须遵循唯一默认 loop 的事件结构 |

这些是设计参考，不意味着可直接复制所有代码和资产。Grok 的仓库明确不提供原始前端源码授权，Kandev 根许可为 AGPL，其他参考仓有不同许可文本；具体复用应逐文件核对，首版应独立拥有品牌与视觉资源。[^1]

## 最小领域模型

建议最初就分清下面几个概念，但是否拆成独立表由实现时确定：

| 对象 | 负责什么 | 生命周期 |
|---|---|---|
| Bot Profile | 身份、职责、偏好、记忆范围、默认执行策略 | 长期 |
| Task/Thread | 用户目标、约束、可见交流与验收 | 可跨多次运行 |
| Execution | 一次具体指派及其状态、产物与执行者 | 有开始和终态 |
| Native Session Binding | provider 原生会话、版本、配置根引用 | 可跨多轮 execution，也可能失效 |
| Workspace/Computer | 文件、Git、运行地点与可用工具 | 与 Bot、执行进程分开 |
| Interaction/Artifact | 人类待决事项与工作结果 | 持久且可追溯 |

目标层可以有一条主时间线，Worker 拥有自己的执行历史。父子关系、普通 fork、同项目和共享工作区是不同关系，不能全用 parent_id 暗示。Cindy 的 Orca 与 fork 字段分离、AO 的稳定 session 与 native session 分离，提供了相应证据。[^2][^3]

不建议首版引入通用 DAG 引擎。先支持有依赖的少量任务和明确的主管派发，只有真实场景要求分支、补偿和重试步骤时再扩展。

## 控制面、执行服务与协议

概念结构是“产品控制面—执行宿主—driver—原生 agent”。产品控制面拥有任务、调度、交互与结果；执行宿主管理进程、原生 session 和工作区；driver 翻译协议；原生 agent 继续拥有自己的模型与工具循环。

可以 ACP-first，但要建立真实 capability 而非共同最小功能集。Kandev 的统一 ACP factory 仍配有方言与 enricher，说明统一协议后仍需处理事件和配置差异。[^4]

首版本地执行宿主可与控制面位于同一程序，但接口和所有权明确。若“关闭 UI 后继续工作”是首版需求，进程寿命就必须独立于窗口。不要在没有实际远端需求时先搭控制集群，也不要让 UI 直接拥有所有 CLI 子进程。

原生协议作为有理由的例外。若某项关键能力只有原生路径可用，允许一个 driver 使用它，但上层不泄漏 provider DTO。协议路线通过验证后决定，不能将“纯 ACP”视为无需权衡的架构正确性。

## 分阶段演进

### 阶段 0：把产品价值收敛到一个工作故事

选择一个可核验任务，例如伙伴接收开发目标，主管拆出实现和测试/审查，两个不同引擎 Worker 产出变更与报告，用户可以插话，并最终看到一个整合结果。

定义保留 Grok 体验的具体部分：伙伴入口、连续消息、背景工作、需要用户时再打扰。若同时要求邮件助理、任意桌面、手机控制、团队 SaaS 和自主开发，独立路线会在证明核心前失控。

退出条件是一组可观察的任务步骤、交互状态和成果标准，明确哪些首版不做。此阶段只需要设计和可行性验证，不先发布通用 SDK。

### 阶段 1：单引擎完整闭环

先接一个原生引擎，支持创建、发送、多轮、流式、权限、停止、原生恢复和产物访问。产品历史独立保存，记录 prompt 是否被接受；接受不明时不自动重发。

早期就完成中断与故障语义，避免只把 happy path 做漂亮。控制通道断开、原生进程退出、用户取消、权限等待分别记录。退出条件是用户可以真实完成并继续同一个任务，关闭界面后状态不丢。

### 阶段 2：第二引擎检验抽象

以同样的工作故事接第二个引擎，允许明确的能力差异。统一事件只覆盖产品需要理解的语义；保留原生原始事件的诊断引用，但不要让整个前端依赖它。

将同 turn steering、下一轮排队、fork、文本交接等定义为不同能力。Cindy 的 capability 原因模型和 AO 的 Chat 门槛可以作为参考。[^5]

退出条件是第二个 driver 不要求改写伙伴/任务对象，UI 不需要大量按引擎名称判断；必需能力无法实现时明确收窄首批支持，而不是伪造事件。

### 阶段 3：主管与完整 Worker

主管是具有委派工具的普通原生 session。平台保存工作项、归属、回传和验收，模型提出决策但不直接成为数据库状态的唯一来源。一个 Worker 完成后仍可追问，空闲时可释放运行资源而保留身份。

工作投递使用持久 message ID 与接收确认；重复回传只更新一次产品结果。并行写代码使用独立 worktree，或者明确串行共享策略。达到最大并发、等待资源、等待审批都是可见状态。

退出条件是主管用一种引擎，Worker 用另一种，用户能独立中断 Worker，主管能基于产物与验证继续推进，而不是只接受“完成了”。

### 阶段 4：引擎交接与恢复

在 idle 边界先实现显式切换，再处理运行中停止后的切换。持久记录源/目标 execution、交接材料、源停止证据、目标接受证据和当前有效代次，禁止两个控制器同时取得执行权。

优先保留原生 session 以便切回；目标第一次出现时使用明确的交接材料。材料以目标、约束、实际工作状态、结果引用和未完成事项为主，必要时检索原文。参考 Cindy 的 full/delta 与 AO 的持久流程，但不盲目照搬其全部字段。[^2][^3]

退出条件是每个切换节点发生崩溃都可解释，并能恢复或等待用户；原生 session 失效被明确说明，不能把文本重建当作原生 resume。

### 阶段 5：长期伙伴与共享工具

在可靠执行之上加入可纠正记忆、routine、Bot 间协作与一个通用应用工具场景。共享工具由产品以 MCP 等接口提供，原生编码工具仍由 agent 保留。

定时任务有独立 occurrence 与补跑策略，背景更新聚合后再通知主管。长期记忆避免收集全部日志，区分偏好、项目约束和一次性任务指令。

退出条件是同一伙伴跨任务延续，用户不用管理 native session，同时能查到每次后台动作的来源与结果。

### 阶段 6：跨机器与扩展生态

只选择一个远端执行场景：将执行宿主放入目标主机或容器，让控制面不直接依赖该机器路径。加入认证、版本握手、产物传递和断线续接。执行地点变更与引擎变更是两个迁移维度，应分别验证。

第三个 driver 和第二个执行环境跑通后，再固化对外插件接口。否则接口很可能只是第一版内部设计被过早公开，后续难以演进。

## 四个必须先设计清楚的机制

### 事件与状态

建议保存能支持恢复的持久事实，并让 UI 从事实投影。不要存整套实时 token 流来冒充持久可靠性，也不要仅保留最终 assistant 文本。至少要知道命令意图、接受状态、原生会话绑定、交互、终态和产物。

外部 agent 的可观察日志不是完整内部推理。DSH 的“模型可见即入日志”适用于其控制的 loop；接外部 harness 时只能对自己发出和收到的材料作保证。[^6]

### 工具与权限

产品工具权限和原生 agent 权限分别处理。仅通过 MCP 限制共享工具，并不约束原生 shell；需要配置原生 sandbox 或在执行环境施加边界。账号凭证引用进入配置，密钥不进入共享交接材料。

用户授权绑定动作和范围，不把上一个 agent 的“已批准”文字当作新引擎的任意授权。遇到外部动作结果未知，先检查实际结果或停下澄清，而非自动重放整轮任务。

### 交接与记忆

长期 Profile、产品历史、原生 context 和共享记忆分别治理。任务连续性通过显式材料与真实文件维护；不同引擎的 compaction 或隐藏推理不尝试移植。

记忆需要可查看、纠正、删除和限定范围。否则多个 agent 使用同一错误记忆，会把一次错误扩大为团队持续行为。

### 验收与成果

Execution completed 只表示执行结束，Task accepted 表示满足验收。测试命令退出码、diff、文件摘要、审查结论与未验证项都应保留来源。主管可提出验收结论，但系统要保留其依据以便用户复查。

## 实现投入与范围控制

| 工作包 | 初期投入 | 持续成本 |
|---|---|---|
| 产品身份/任务/事件 | 中 | 数据迁移与产品扩展 |
| 两个原生 driver | 高 | 上游协议、认证和版本兼容 |
| 执行宿主与恢复 | 高 | 进程、平台、升级、故障诊断 |
| 工具/审批/产物 | 高 | 外部服务与权限语义 |
| 伙伴消息 UI | 中 | 丰富事件与长历史性能 |
| 多端与远端 | 后置高 | 部署与兼容矩阵 |
| 插件生态 | 后置高 | 版本和分发承诺 |

这条路线的初期成本通常高于在匹配底座上增量开发，但“长期一定更便宜”也不能预先证明。应记录每个新增引擎需要改动哪些层、每次协议升级修复成本、恢复失败诊断时间、主管与 Worker 的冗余 token。只有这些指标改善，独立核心的边界价值才真正兑现。

人员能力应覆盖产品交互、异步进程与协议、持久数据与恢复、真实 agent 集成测试。不能将全部建设视为前端聊天应用。工期需由首两个 driver 的验证结果决定，不给出没有依据的固定周数。

## 主要失败模式与停止条件

| 失败模式 | 预警信号 | 调整方向 |
|---|---|---|
| 先造框架后找产品 | 插件、DAG、远端齐全，真实任务仍跑不完 | 回到一个工作故事和两种引擎 |
| 偷偷重写 agent loop | 为统一工具和审批绕开原生行为 | 调整契约，保留原生执行主体 |
| 最低共同能力缩水 | 高级能力被统一移除 | 可选 capability 与显式降级 |
| 第二套 Grok Router | 每轮新进程、只有文本拼接 | 将 native resume 和交互作为首要门槛 |
| 无限自动重试 | 重启就重放 prompt，副作用重复 | 接受凭据、状态核对和未知态 |
| 全量上下文共享 | 成本飙升、角色混淆、记忆污染 | 任务包、成果引用、按需检索 |
| 重复建设执行基础设施 | 本地、SSH、容器各一套生命周期 | 一个执行宿主契约，逐种扩展 |

若第二引擎必须修改大部分产品逻辑，说明抽象仍以首个引擎为中心；若恢复持续不可靠，优先复用 AO 的设计或现成服务边界，而不是通过隐藏错误改善演示。

## 验证与演进纪律

不存在既有用户数据，不代表可以忽视迁移。首个可用版本起就为事件与 native session binding 标版本，保留可导出的任务、历史和产物引用。每次升级先验证旧数据可读，再启用新写路径。

| 核心验证 | 通过标准 |
|---|---|
| 真实两引擎完整任务 | 可继续、可停止、可回应交互、成果可验证 |
| prompt 接受边界断线 | 不重发未知请求，不生成双执行 |
| 产品进程被杀 | 任务能重连或明确进入恢复态 |
| 双客户端审批 | 一个有效回应，另一方得到已处理 |
| 重复 Worker 回传 | 只推进一次，保留来源证据 |
| 切换源退出延迟 | 不启动可并发写入的目标 |
| 同工作区并行 | 通过隔离或调度避免未授权冲突 |
| 新旧版本读取历史 | 不丢失事实，不静默错误投影 |

“对外效果 exactly-once”不能仅靠本地队列保证。对于支持幂等键的外部服务可使用该能力；其他情况保存动作与结果证据，未知时查询实际状态。这应是产品恢复承诺的一部分。

## 路线裁决

独立路线适合有明确长期产品主张、能控制范围并愿意承担基础可靠性建设的团队。它最有价值的产物是清楚的所有权和可扩展的产品模型，不是一套新的模型 loop。

最初的三个验证应为单引擎完整恢复、第二引擎不污染产品层、混合团队可验证交付。通过后再投入伙伴长期记忆、跨主机和插件生态，能显著降低做出漂亮但不可持续演示的风险。
